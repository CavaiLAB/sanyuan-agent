# SanYuanAgent

[匠心智能体平台](https://github.com/CavaiLAB/jiangxin)的智能体引擎，一个独立运行的 SDK。Python 3.12：推理循环、工具、技能、记忆、沙箱、模型路由、多 Agent 编排。

> **状态（2026-11-17）：核心已经带着历史迁入本仓库的 `packages/core`，并改了名；服务层与媒体适配层还在原仓库，随后再迁。下文讲架构与对接平台的部分仍是规划稿。**
>
> 代码来自私有产品里的 Python Agent 引擎。改名后发行名是 `sanyuan-agent`，导入名是 `sanyuan_agent`，命令行是 `sanyuan-agent`，环境变量前缀是 `SANYUAN_AGENT_`。迁移的做法与进度见[迁移与改名](docs/migration.md)。

## 定位

平台的理念叫「三元全智生命体」：三元给躯体，全智给心智，生命体给活法。SanYuanAgent 承担「全智」，也就是心智：理解人的意图，规划，选择并调用工具，记住经验，在反馈里改进。名字取自整个理念的头两个字，不表示它对应其中的「三元」。

它是工站、产线、工厂三级智能体的大脑，要能提供给这三级使用（已定）：

| 层级 | 形态 | 这一级的智能体做什么 |
|---|---|---|
| 工站 | 具身智能体 | 分解工单、编排技能，根据作业结果调整计划 |
| 产线 | 协同智能体 | 以统一入口调用排程、质检等专业应用 |
| 工厂 | 超级智能体 | 把任务分派给产线、机器人等智能体，协调资源冲突，按执行结果调整方案 |

引擎在每一级具体承担到哪一层是提议，三级各怎么打包与部署是规划，见[框架架构](docs/architecture.md)第 13 节与平台总览的[三种形态](https://github.com/CavaiLAB/jiangxin/blob/main/docs/08-industrial-forms.md)。

它是一个独立运行的 SDK（已定，2026-11-17）：每个端都要用到它，包括机器人这类边缘设备，装上就能用。目标是不接平台时它自己能完整运行；现在离这个目标还差什么，见[独立运行的 SDK](docs/sdk.md)。

它是引擎，不是产品。它不保存用户、租户、权限这些业务主数据，也不做界面。接入平台之后：

- 身份、权限、能力目录、审计由 [Kun](https://github.com/CavaiLAB/kun) 提供；Agent 之间的协同与人审提议也由 Kun 承担。见[接入平台：与 Kun 的交互](docs/platform.md)。
- 模型服务由 Kun 提供（已定）。设备本地可能还有小模型（已定），两边怎么一起用见[与模型服务的交互](docs/models.md)。
- 界面由 [Qian](https://github.com/CavaiLAB/qian) 提供。

## 组成

| 部分 | 内容 | 许可现状 |
|---|---|---|
| 核心 | 推理循环、工具、技能、记忆、沙箱接口、模型供应方、多 Agent 编排。可以脱离其他部分单独安装 | Apache-2.0 |
| 服务层 | 对外的服务接口：对话与运行、流式输出、工作流、模型治理、技能同步、用量记账 | 没有开放 |
| 媒体适配层 | 多模态能力的适配 | 没有声明 |

铁律：服务层可以引用核心，核心不得引用服务层。有检查强制这个方向，也有检查保证核心能单独装上、命令行起得来；检查不包括跑通一个 Agent。

核心保持 Apache-2.0（已定，2026-11-17），版权与所借鉴上游项目的许可见 `packages/core/NOTICE`。服务层与媒体适配层迁入之后用什么许可，待定；平台的后端与前端已定全部用 MIT。

## 核心的模块

| 模块 | 做什么 |
|---|---|
| 推理循环 | 基于状态图的循环：规划、行动、执行工具、观察，再规划或收尾 |
| Agent 定义 | 用一份声明描述一个 Agent：提示、模型、工具集、策略 |
| 编排 | 子 Agent 在隔离的状态里运行；工作流引擎把一件事分阶段并发分给多个子 Agent，再汇总 |
| 工具 | 工具注册表与提供方接口；内置工具：网页检索与抓取、文件、终端、浏览器、多模态、技能执行 |
| MCP | MCP 客户端，以及把外部工具接进工具注册表的桥。传输只有本地进程一种，客户端还没有接进运行路径 |
| 安全 | 三类安全组件：按 Agent 配置的工具策略（允许、拒绝、需确认）、高风险动作识别、提示注入检测 |
| 技能 | 读取 `SKILL.md` 形式的技能；自带技能随发行版可信；自定义技能要有签名，校验不过的不加载 |
| 记忆 | 感知、工作、情节、长期四层；访问范围分个人、团队、租户；上下文分个人、项目、会话 |
| 模型 | 模型供应方注册表，按顺序回退 |
| 用量 | 记录每次调用的用量 |
| 沙箱 | 沙箱提供方接口，有本地实现与桌面本地实现；云上的沙箱经服务层接入 |
| 产物与知识 | 产物的收集；文档切分、入库与检索 |
| 事件流 | 运行过程对外输出的事件定义：步骤、工具调用、产物、最终回答等 |

## 设计原则

1. **核心能单独安装，目标是装上就能用。** 核心不引用服务层；它和平台的耦合只有产物上传一处。「装上就能用」是已定的目标，现在还差什么见[独立运行的 SDK](docs/sdk.md)第 9 节。
2. **可替换的地方都是注册表或接口。** 工具、记忆后端、沙箱后端、模型供应方都可以换。
3. **工具调用可以受策略约束。** 引擎里有工具策略与确认的机制。它们是对平台权限判定的补充，不代替它。
4. **技能要可信。** 来源不明、没有签名的技能不加载。
5. **记忆有归属。** 每条记忆都有访问范围和上下文层级，召回只在允许的范围里进行。
6. **模型可换。** 引擎不绑定某一家模型。模型可以在平台上，也可以在设备本机。

## 迁入平台之后要变的

| 事项 | 现在 | 迁入之后 |
|---|---|---|
| 身份 | 以用户的身份运行 | 以 `agent` 主体运行，令牌里带委托链，由 Kun 签发 |
| 能调用什么 | 自己的工具注册表 | 另外从 Kun 的能力目录按范围取可用的能力 |
| 技能、子 Agent、钩子从哪来 | 引擎自己的目录与同步机制 | 从平台的插件树按范围取 |
| 多 Agent | 编排者把活分给工作者，工作者之间不通信 | 加上跨人的协同：经 Kun 的信箱收发消息，只执行人批准过的 |
| 人的确认 | 引擎里有工具策略与确认的机制 | 加上完整的流程：人在界面上确认，运行暂停后恢复 |
| 审计与计量 | 引擎内记录 | 交给 Kun 统一留存 |
| 模型 | 经模型网关调用上游模型 | 平台的模型服务由 Kun 提供；设备上另有本机小模型，按策略路由 |
| 与平台的对接 | 基本都写在服务层里 | 经平台连接器接 Kun：设备只向外连；设备上有本机模型时断网可运行 |
| 部署形态 | 作为集群里的服务运行，核心可以单独安装 | 独立运行的 SDK：库、命令行、本机常驻进程、集群服务四种用法，覆盖云上、桌面与边缘设备，提供给工站、产线、工厂三级 |

这些都是规划，见[框架架构](docs/architecture.md)，以及下面三份展开的文档。最后三行里除了「模型服务由 Kun 提供」「独立运行的 SDK」这两处已定，具体的做法都是提议。
