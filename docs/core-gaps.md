# 核心的差距与提议

> 状态：提议（2026-11-17）。本文没有已定的内容，全部待产品负责人确认。「已有」「没有」说的是本仓库 `packages/core` 里的核心，对着代码核过。服务层与媒体适配层还没有迁入，本文不涉及它们。
>
> 本文对照的是七个成熟的智能体框架，下称对标项目，按文档的规矩不写名字。七个里有模型厂商自己的开发包与运行框架，有开源的编码代理与个人助理，也有云厂商的开发包。它们的能力取自各自公开的文档与开源仓库（2026-11-17），标着实验性或预览的不算「有」。这个领域变得快，本文的对照隔几个月要重看。

## 1 结论

核心现在是短任务的形态：一次运行在内存里走完，缺省十轮，工具逐个执行，上下文超了就裁掉旧消息。对标项目面向的是长任务，它们在循环、上下文、工具执行这一层收敛出了一组共同的能力。第 2 节列了十八项：核心有十一项没有，六项只有一部分，一项不在本文展开。

其中两项是地基，别的能力都搭在它们上面：

- **会话日志。** 每次运行的全过程都记进一份只追加的事件日志。在成熟的做法里，恢复、分叉、挂起与续跑、回放、轨迹导出都从它派生。本文提议起步时续跑先靠状态图框架的快照，见第 3.2 节。
- **生命周期事件点。** 循环和工具执行管线上可以挂监听器的位置。策略、确认、审计、遥测、平台的钩子都落在这里。

[独立运行的 SDK](sdk.md)第 9 节已经列了离「装上就能用」的差距：入口、依赖、本机状态、发布、平台连接、MCP、断网、本机常驻。本文不重复那张表，补的是它没有提到的能力，并提议一个先后。

几个词在本文里的意思：

- **轮**：请求一次模型，加上它要的工具调用。
- **运行**：从一次输入到给出最终回答，由若干轮组成。
- **会话**：前后相接的若干次运行，对应[框架架构](architecture.md)第 10 节的线程。会话日志一个会话一份，每次运行往后追加。

下文的代码路径都在 `packages/core/sanyuan_agent/` 之下。

## 3 逐项：成熟的做法、现状、提议

### 3.1 会话日志

**成熟的做法。** 每次运行的全过程都记进一份只追加的事件日志。原则是模型看得到的内容都进日志：系统提示、每条消息、工具调用与结果、压缩、确认请求与回答。日志是事实源，下面这些都从它派生：

- 恢复：进程退出之后，接着上次的运行往下做。
- 分叉：从某一步另起一支，原来的一支不动。
- 回放：拿录下的模型响应重跑，用来测试。
- 展示与导出：界面读的事件流、交给评测的轨迹，是同一份日志的投影。

**核心现状。** 一次运行的状态只在内存里：消息、工具结果、迭代次数、累计用量（`agents/simple.py`）。运行结束后留下的是记忆，也就是情节摘要与长期记忆，不是可以接着跑的记录。对话的线程与消息不在核心里，见[框架架构](architecture.md)第 2 节的分层，以及第 14 节的「业务服务放在哪里」。

**提议。**

1. 核心里加会话日志：一个会话一份，每次运行往后追加；带序号，一行一个事件。
2. 日志的格式写成契约，和事件流是同一份。事件流是日志的实时投影，不另定义一套事件。这份契约三个框架都要用，放在哪里、怎么生成各语言的类型，按平台总览[总体架构](https://github.com/CavaiLAB/jiangxin/blob/main/docs/02-architecture.md)第 7 节的约定。
3. 后端可换。本机后端是状态目录里的文件，符合[独立运行的 SDK](sdk.md)第 2 节「状态都在本机」；集群里由服务层接数据库后端。
4. 设备上等着补传的运行记录与用量从日志里取，不为这两样另存一份。报多细按策略，见[接入平台：与 Kun 的交互](platform.md)第 12 节。上报类的平台能力调用仍按该文第 9 节进本机队列。

### 3.2 挂起与续跑

**成熟的做法。** 运行可以停在一个明确的点上等外部的回答，例如等人批准一次工具调用，或者等一个耗时的外部任务。挂起的时候状态已经落盘，进程重启也不丢。回答到了，从挂起点接着跑。

**核心现状。** 没有检查点、中断与恢复。人确认之后恢复运行的完整流程，[框架架构](architecture.md)第 4 节记为规划。

**提议。**

1. 挂起点是一种事件：记进会话日志，写明等的是什么、谁可以回答。
2. 回答从哪里来由调用方决定：命令行里问人，库里走回调，接入平台时交给平台的审核流程。这和[独立运行的 SDK](sdk.md)第 4 节的端口划分一致。
3. 没有人在场时按策略处理：等待，或者直接拒绝。
4. 实现上，核心用的状态图框架（LangGraph）自带检查点与中断，核心现在没有用。起步可以先用它：续跑靠它的快照，快照要另配落盘的存储；会话日志照常记全过程，挂起与恢复各记一条事件。会话日志的契约不依赖它的快照格式。以后要不要改成从日志恢复，列在第 5 节。

为什么要紧：发给 Agent 的内容、Agent 发出去的内容都要由人审核，起步两道都必审（已定，见平台总览的 [Agent 协同](https://github.com/CavaiLAB/jiangxin/blob/main/docs/04-agent-collaboration.md)第 1 节）。人审、设备断网后的补传、人确认后恢复运行，都要求运行能停下来、能接着跑。

### 3.3 生命周期事件点

**成熟的做法。** 循环和工具执行管线上有一组固定的位置可以挂监听器。常见的位置：会话开始与结束、收到用户输入、请求模型之前、工具执行之前、工具执行之后、压缩之前、子 Agent 结束、运行停止。监听器分两类：只观察的，和环绕的。环绕的可以改写输入、拒绝、要求确认，或者替换结果。有的对标项目把权限判定、沙箱、审批本身就做成工具执行之前那个事件上的监听器，循环里没有特例。

**核心现状。** 核心没有可以登记监听器的事件点。现有的只是只读的观察口：运行的事件流、子 Agent 运行上的工具事件回调、模型调用库的全局回调。要在工具执行或请求模型的前后改写、拒绝，只能改核心的代码，或者由调用方在外面包一层。平台的组件模型里有钩子这一类表面，引擎这一侧现在没有它可以对应的位置。

**提议。**

1. 在核心里定义一组事件点，名字与载荷写成契约。起步的一组：运行开始、运行结束、请求模型之前、模型响应之后、工具执行之前、工具执行之后、压缩之前、挂起、恢复、子 Agent 开始、子 Agent 结束。
2. 每个事件点写明是观察还是环绕，这是契约的一部分。
3. 策略判定、确认、审计、遥测都接成监听器。
4. 插件里声明的钩子，在引擎里对应到这些事件点。环绕的监听器只能收紧：可以拒绝、可以要求确认，不能把排在它前面的拒绝或要求确认改成放行。这和[独立运行的 SDK](sdk.md)第 4 节「本机配置可以收得更紧，不能放得更宽」是同一个道理。谁可以登记、先后怎么排，写进契约。
5. [框架架构](architecture.md)第 14 节有一项待定：Python 侧是否实现与后端同语义的组件运行时。提议不整套实现：事件点加上已有的注册表与提供方接口，先够用。

### 3.4 MCP

差距已经列在[独立运行的 SDK](sdk.md)第 9 节：客户端没有接进运行路径，传输只有本地进程一种。对标项目都支持远程传输。

**提议（补充）。**

1. 接进运行路径，补上远程传输与授权。
2. MCP 工具的定义缺省不全部交给模型，按需加载，见第 3.6 节。
3. MCP 工具的结果同样受大小上限的约束，见第 3.6 节。

为什么要紧：设备的技能、平台的能力、社区组件里的 MCP 声明，三处都提议经 MCP 接入，分别见[独立运行的 SDK](sdk.md)第 7 节、[接入平台：与 Kun 的交互](platform.md)第 6 节、[框架架构](architecture.md)第 11 节。

### 3.5 对外入口

差距已经列在[独立运行的 SDK](sdk.md)第 9 节：命令行的运行入口没有做完，编程接口没有定型。事件名与前端契约是两套，见[框架架构](architecture.md)第 10 节。

**成熟的做法。** 一套循环给出几种接入：交互、单次运行、流式的事件输出、标准输入输出上的远程调用，另有可以嵌进程序的库。有的对标项目让命令行做唯一的事实源，桌面端与移动端读同一份投影，界面不存业务状态。

**提议（补充）。**

1. 接口的冻结排在第 3.1 至 3.3 节定型之后。恢复、分叉、回答确认请求都是接口的一部分；先冻结再补，就是破坏性变更。改向与打断的接口（第 3.7 节）也在冻结之前定下来，实现可以放在后面。
2. 库、命令行、本机常驻进程三种用法读写同一份会话日志，用同一份事件协议，不各存各的状态。

### 3.6 上下文工程

**成熟的做法。**

- **缓存友好的提示组装。** 模型服务按请求的前缀缓存，前缀一变缓存就失效。所以系统提示和工具定义在一次会话里保持不变，随轮变化的内容追加在后面。几个对标项目把这一条当成架构约束，写进了贡献规范或测试。
- **压缩。** 接近上限时把较早的历史摘要成一条，保留最近的原文；原始记录留在会话日志里。
- **大输出落盘。** 工具结果超过上限时全文写进文件，上下文里只留头尾和文件路径。
- **工具定义按需加载。** 工具多的时候，模型先只看到一个检索入口，用到哪个再载入它的定义。
- **项目指令文件。** 从工作目录和上级目录读一个约定名字的文件，拼进系统提示。社区里通行的名字是 `AGENTS.md`。

**核心现状。**

- 每一轮都重新拼消息：工作记忆的摘要、命中的技能正文、召回的记忆各作为一条消息插在序列的最前面，排在系统提示之前；每轮的提醒追加在最后（`agents/simple.py`）。工作记忆的摘要随步骤增加而变，所以带着工作记忆运行时，系统提示和它后面的内容进不了稳定的前缀。召回的内容随每次运行的输入变。裁剪一旦发生，前缀也跟着变。核心不向模型服务声明缓存位置，用量里不记缓存命中。
- 上下文的预算缺省是 24000 token，按字符数估算。超了就裁掉较早的消息，保留开头的系统消息、最早的那条任务消息和最近的消息（`memory/context.py`）。工作记忆带可选的摘要压缩，要调用方注入摘要函数并把工作记忆放进运行状态才生效。
- 工具结果没有统一的大小上限，也没有落盘。网页类工具各有自己的预算。
- 每一轮把全部已启用工具的定义交给模型。技能是按需加载的。
- 不读项目指令文件。

**提议。**

1. 把「一次会话里系统提示与工具定义不变」定成核心的约束。召回的记忆、工作摘要、命中的技能正文改为追加在消息序列的后部。每轮的提醒现在已经在末尾。记忆什么时候召回、哪一部分常驻在前缀里，见[记忆的模型](memory.md)第 4.3 节。
2. 向支持的模型服务声明缓存位置，用量里记缓存的读与写。
3. 用压缩取代裁剪：摘要留在上下文里，原文留在会话日志里。压缩可以交给便宜的模型做。
4. 工具的声明里加结果的大小上限；超了落盘，只留头尾与路径。
5. 工具多于一个阈值时改为按需加载。载入的定义追加在消息序列里，不改动开头的工具定义，不破坏第 1 条。
6. 读项目指令文件。在设备上，它装的是这台设备、这条产线的作业约定。它和技能正文一样是给模型的指令，来源要不要校验列在第 5 节。
7. token 的估算用模型服务回报的用量来校准。

为什么要紧：设备上的小模型上下文更短。[与模型服务的交互](models.md)第 4、5 节提议在模型目录里登记每个模型的上下文长度，并把长上下文的步骤交给平台的模型，后一条缺省不开。

### 3.7 循环

**成熟的做法。**

- 运行中可以追加消息：一种在当前这批工具执行完之后插入，一种等这次运行自然停下再送。也可以随时中止，已经产生的输出保留。
- 工具并行执行。只读的并行，会写入的串行，由工具声明或由白名单决定。
- 对标项目过半不设轮数上限。兜底靠的是时间与 token 的预算、重复调用的检测和熔断。
- 思考强度是一项运行参数。模型不支持所要的档位时，取它支持的最近一档。

**核心现状。** 一批工具调用逐个执行（`agents/tool_executor.py`）。轮数上限缺省是 10（`config/spec.py`）。单个 Agent 的运行和工作流都没有改向与打断的接口：调用方关掉事件流，在跑的任务随之取消。Agent 的声明里没有思考强度，也没有输出的 Schema。连续失败的熔断是已有的。

**提议。**

1. 加改向与打断的接口。追加的消息作为事件进会话日志。
2. 工具的声明里已有副作用这项元数据（`tools/provider.py`），现在只作描述，登记进注册表时没有带过去。提议把它带到执行这一步：声明为只读的并行，其余的和没有声明的一律串行。
3. 轮数上限改成可选，另加时间与 token 的预算、重复调用的检测。退到本机小模型时仍按[与模型服务的交互](models.md)第 6 节调低上限。
4. Agent 的声明里加思考强度。另加输出的 Schema：它不在第 2 节的对照里，是[与模型服务的交互](models.md)第 6 节「输出按结构化的格式约束」要用到的。
5. 对标项目的内循环都不是建在图框架上的。核心的循环建在状态图框架上。要不要继续，本文没有提议，列在第 5 节。

### 3.8 轨迹、追踪、评测

**成熟的做法。** 轨迹导出和分段的追踪是普遍有的：一次运行按轮、模型调用、工具执行分段，带用量与耗时，用 OpenTelemetry 导出。内置的评测并不普遍，只有少数有完整的一套。有的对标项目用假的模型按录下的响应回放，做确定性的测试。

**核心现状。** 有运行事件的定义（`sse.py`）和每次调用的用量计量，另有少量指标。没有运行一级的追踪，没有轨迹的导出格式，没有评测。[独立运行的 SDK](sdk.md)第 8 节把「评」排在发布之前，评什么、拿什么数据评、过不过由谁定是待定。

**提议。**

1. 轨迹就是会话日志的导出，不另定格式。
2. 追踪的分段挂在事件点上：运行、轮、模型调用、工具执行。
3. 加回放测试：一个假的模型供应方，按会话日志里录下的响应作答。
4. 评测的最小形态：一组任务，每个任务带判据。判据可以是规则，也可以是由另一个上下文里的评审模型按评分表来判。结果进发布之前的门禁。拿什么数据评、过不过由谁定，仍然没有提议。

### 3.9 定时与事件触发的运行

**成熟的做法。** 一次运行不一定由人发起：可以按时间表，可以由外部事件触发，Agent 也可以给自己排后续的运行。每次触发是一次全新的运行，结果投递到指定的地方。

**核心现状。** 没有。核心里的调度只管回收（`gc/scheduler.py`）。

**提议。**

1. 引擎一侧只做两件事：一次运行可以带着触发的来源启动；没有人在场时，需要确认的动作按策略等待或拒绝。
2. 本机常驻进程带一个简单的时间表。设备本机的事件经本机通道提交，见[独立运行的 SDK](sdk.md)第 3 节。断网时，设备上有本机模型的，本机的时间表与本机的事件在策略允许的范围里照常触发运行，见[接入平台：与 Kun 的交互](platform.md)第 9 节。
3. 接入平台时，平台一侧的时间表与事件经下发任务的通道到设备，见[接入平台：与 Kun 的交互](platform.md)第 4 节。引擎不为它们另做一套。两边怎么接待定，列在第 5 节。

为什么要紧：在工站与产线上，运行多半由工单和设备事件发起。

### 3.10 从经验沉淀技能与记忆

**成熟的做法。** 最完整的一套是这样的：

- 一次运行结束之后，在后台另起一次复盘，不占主循环。
- 复盘看这次对话，先修补用过的技能，再考虑新建；把有依据的事实写进记忆。
- 产物可以设成先暂存、等人批准。
- 长期不用的技能定期归档，不删除。每次改动记账，可以回滚。

**核心现状。** 每次运行结束时存一条情节记录：用户的输入与最终回答；有长期记忆的读写工具与回收。没有把做法沉淀成技能的机制。

**提议。**

1. 加运行结束之后的复盘，产物是技能与记忆的草稿。
2. 技能的草稿走技能已有的规矩：校验、签名。起步一律等人批准。记忆的草稿按范围分：个人范围的自动生效、可以回滚，共享范围的要批准，见[记忆的模型](memory.md)第 4.2 节与第 5.2 节。
3. 改动记账、可以回滚，只归档不删除。
4. 复盘可以交给便宜的模型做。

记忆这一半见[记忆的模型](memory.md)：运行结束之后的提取在第 4.1 节，跨会话的整理在第 4.2 节。

提议让这一项走平台总览里自然语言构建的那条管线：智能体出草稿，校验器把关，人批准。见[一切皆插件](https://github.com/CavaiLAB/jiangxin/blob/main/docs/03-plugin-model.md)第 7 节。

### 3.11 持久的任务板

**成熟的做法。** 有的对标项目把多智能体分成两种原语。一种是函数调用式的分派：子 Agent 在隔离的上下文里跑完，只交回结论。另一种是持久的任务板：任务落在存储里，可以认领、阻塞、评审，进程崩溃之后可以回收，由不同的进程甚至不同的机器来做。

**核心现状。** 第一种已有：子 Agent、把子 Agent 当工具、工作流。第二种没有。工站、产线、工厂三级之间怎么通信是待定，见[框架架构](architecture.md)第 13、14 节。

**参照。** 本文不提议做法，只给那项待定提供一个参照：一级之内的分派沿用已有的编排；跨级的往来是持久的队列，不是函数调用。它和平台的协同信箱是什么关系、要不要逐条人审，按平台总览的 [Agent 协同](https://github.com/CavaiLAB/jiangxin/blob/main/docs/04-agent-collaboration.md)来定。

### 3.12 权限的表达与隔离手段

这一项只列方向。核心有哪三类安全组件见[框架架构](architecture.md)第 4 节，沙箱的后端见第 7 节，现状不在本文展开。

对标项目在这一项上分成两派。多数提供权限模式与审批，其中少数另有完整的系统级沙箱与出口管控。也有明确不做隔离、把边界交给容器的。可以参照的做法：

- **权限模式。** 从只读到全部放开的几档，一次运行选一档。
- **带参数的规则。** 规则不只看是哪个工具，也看调用的参数。
- **审批挂在事件点上。** 见第 3.3 节。
- **让另一个模型分担低风险的确认。** 人只看拿不准的。这说的是工具调用的确认。协同消息的审核怎么减负是另一回事：起步出站、入站两道都必审已定，以后放不放宽待定，见平台总览的 [Agent 协同](https://github.com/CavaiLAB/jiangxin/blob/main/docs/04-agent-collaboration.md)第 4.5 节。
- **隔离手段按设备的能力选。** 做不到隔离时关掉哪些工具，[独立运行的 SDK](sdk.md)第 5 节已有提议。
- **执行环境里不放真实的凭据。** 由外面的代理在出站时替换。

## 4 先后

提议分四步。任务板不在图里，它取决于三级之间怎么通信那项待定。

```mermaid
flowchart LR
  A["第一步<br/>会话日志<br/>生命周期事件点"] --> B["第二步<br/>挂起与续跑<br/>接口与事件协议定型<br/>MCP 接进运行路径"]
  B --> C["第三步<br/>上下文工程<br/>改向、并行、预算"]
  C --> D["随后<br/>轨迹与评测<br/>定时与事件触发<br/>复盘"]
```

- **契约先于接口的冻结。** 第一个包不必等本文的契约：它的形态照[独立运行的 SDK](sdk.md)第 10 节的提议，接口标明还没有冻结。发出第一个包是平台总览[路线与迁移](https://github.com/CavaiLAB/jiangxin/blob/main/docs/06-roadmap.md)里引擎迁入阶段的完成条件，本文不给它加前置条件。承诺接口稳定之前，把第 3.1 至 3.3 节的契约定下来：会话日志、挂起与回答确认请求、事件点。改向与打断的接口、「系统提示与工具定义不变」这条约束，也在那之前定。
- **定契约不动行为，可以先做。** 实现是对核心行为的改动。过渡期能不能先在本仓库改核心的行为还是待定，见[迁移与改名](migration.md)第 2 节。实现排在那一项定了之后。

## 5 待定

提议先定这三项，别的可以随后定：

1. 采纳哪些差距、按什么先后做。
2. 过渡期能不能先在本仓库改核心的行为。它决定实现什么时候能开始。
3. 会话日志与事件流是不是同一份契约。它牵动前端的事件契约。

| 事项 | 提议 |
|---|---|
| 采纳哪些差距、按什么先后做 | 按第 4 节 |
| 会话日志与事件流是不是同一份契约 | 是。事件流是日志的实时投影 |
| 挂起与恢复用状态图框架自带的，还是自己实现 | 起步用自带的；契约不依赖它的快照格式 |
| 以后要不要改成从会话日志恢复 | 没有提议。等第一步的契约定了再评估 |
| 内循环要不要继续建在状态图框架上 | 没有提议。等第一步的契约定了再评估 |
| Python 侧是否实现同语义的组件运行时 | 不整套实现：事件点加已有的注册表，见第 3.3 节 |
| 谁可以登记环绕的监听器、先后怎么排 | 写进事件点的契约；环绕的不能把前面的拒绝或要求确认改成放行 |
| 项目指令文件叫什么、怎么查找 | 沿用社区通行的文件名，从工作目录向上逐级读 |
| 项目指令文件的来源要不要校验 | 没有提议。技能要签名才加载，指令文件同样是给模型的指令 |
| 轮数上限的缺省值 | 改成可选，另加预算与重复调用的检测 |
| 平台一侧与设备本机的时间表、事件怎么衔接 | 平台来的经下发任务的通道到设备；怎么衔接没有提议，见第 3.9 节 |
| 复盘出的技能草稿要不要一律等人批准 | 起步一律等人批准。记忆的草稿见[记忆的模型](memory.md)第 8 节 |
| 评测拿什么数据评、过不过由谁定 | 没有提议 |
| 三级之间用不用任务板 | 没有提议，见第 3.11 节 |
| 过渡期能不能先在本仓库改核心的行为 | 没有提议。登记在[迁移与改名](migration.md)第 2 节与仓库根目录的 `AGENTS.md` |

## 6 不在引擎范围里的

对照里还有几项能力不归引擎：多租户、平台级的身份、权限判定与审计留存、组件的分发归 Kun；界面归 Qian；Agent 之间的协同与人审的规则在平台总览。本文不列它们的差距，见[平台总览](https://github.com/CavaiLAB/jiangxin)。
