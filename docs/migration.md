# 迁移与改名

> 状态：规划稿（2026-11-17）。

## 1 来源

代码在 iClaw 仓库的 Python Agent 引擎目录里，原名 NeuroAgent。它是一个多包的 Python 工作区：

| 部分 | 规模 | 说明 |
|---|---|---|
| 核心 | 约 100 个源文件 | 可以单独安装运行；Apache-2.0 |
| 服务层 | 约 180 个源文件 | 对外的服务接口与业务逻辑；没有开放 |
| 媒体适配层 | 十几个源文件 | 多模态适配，先做了语音合成 |

同一个仓库里还有 C# 服务层和各端应用，它们不在这次迁入的范围里，去向见平台总览的[仓库与归属](https://github.com/CavaiLAB/jiangxin/blob/main/docs/05-repositories.md)。

## 2 已定与待定

已定（产品负责人，2026-11-17）：

- Python Agent 引擎改名 SanYuanAgent。
- 迁入本仓库 `CavaiLAB/sanyuan-agent`：先建仓库写文档，代码之后迁入。
- 它是工站、产线、工厂三级智能体的大脑，要能提供给这三级使用。

待定：

| 事项 | 提议 |
|---|---|
| 迁入的方式 | 引擎带着历史一次导入，不分批 |
| 迁入的范围 | 核心、服务层、媒体适配层三部分一起迁 |
| 发行名与导入名 | 发行名 `sanyuan-agent`，导入名 `sanyuan_agent`；服务层与媒体适配层的名字跟着改 |
| 许可 | 待定。核心现在是 Apache-2.0；平台的后端与前端已定全部用 MIT，引擎是否跟着统一、服务层是否开放，都还没有定 |
| 仓库是否公开 | 待定。现在是私有的 |
| 时点 | 不依赖后端的归并，可以先迁；前提是发行名、许可、是否公开先定下来 |
| 三级的部署形态 | 工站、产线、工厂三级各怎么打包、各依赖什么，待定，见[框架架构](architecture.md)第 13 节。它不卡迁入 |

## 3 改名涉及什么

- 包的发行名、导入名，以及全部源码里的导入语句。
- 命令行入口的名字。
- 配置项与环境变量里带旧名字的前缀。
- 事件流、日志、追踪里出现的服务名。
- 文档与技能说明里的旧名字。

改名一次做完，不保留旧名字的别名包。还在用旧名字的使用方，在迁入的同一个冻结窗口里一起改。

## 4 步骤

提议。

1. **冻结并导入。** 原仓库的 Python 引擎目录进入只读；带着历史把它导入本仓库。
2. **改名。** 按第 3 节一次改完。
3. **验证。** 全部测试通过；「核心不得引用服务层」的边界测试、「核心可以单独安装运行」的测试照旧生效；发出第一个包。
4. **接回去。** 原仓库里用到引擎的地方，改为依赖本仓库发出来的包。
5. **收尾。** 原仓库的引擎目录删除，说明文档指向本仓库。

## 5 迁入时要对齐的事

- **说明文档以代码为准重写。** 迁入时逐条对着代码核对，没有实现的写成规划。安全组件各自在哪些运行路径上启用，是要核对的第一项。
- **统一技能的 front matter。** 社区规范、平台的组件规格、引擎现有实现三处的字段有出入，对齐成一份；引擎对自定义技能的签名要求保留。
- **对接 Kun 的身份。** 迁入平台之后引擎改为以 `agent` 主体运行，这依赖 Kun 先启用 `agent` 主体与委托链。在那之前，引擎保持现有的身份形态。
- **统一事件流的契约。** 引擎输出的事件名与前端契约里的事件类型现在是两套，迁入时对齐成一份跨服务契约。
- **契约的出处。** 现在引擎引用的是原仓库里的契约目录。迁入之后改为引用平台级的契约，两套契约字段的差异在迁入前列清楚。
- **与原仓库其他部分的接口。** 引擎的服务层和原仓库的 C# 服务之间有内部接口。迁入时把这些接口列成清单，逐个确定以后由 Kun 的哪项能力承接。
