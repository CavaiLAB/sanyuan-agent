# 迁移与改名

> 状态（2026-11-17）：第一步「核心带着历史迁入并改名」已经做完，代码在本仓库的 `packages/core`；服务层与媒体适配层还在原仓库。各步做到哪里见第 4 节。

## 1 来源

代码在 iClaw 仓库的 Python Agent 引擎目录里，原名 NeuroAgent。它是一个多包的 Python 工作区：

| 部分 | 规模 | 说明 |
|---|---|---|
| 核心 | 约 100 个源文件 | 可以单独安装；Apache-2.0 |
| 服务层 | 约 180 个源文件 | 对外的服务接口与业务逻辑；没有开放 |
| 媒体适配层 | 十几个源文件 | 多模态适配，先做了语音合成 |

那个仓库的其余部分不在这次迁入的范围里，去向见平台总览的[仓库与归属](https://github.com/CavaiLAB/jiangxin/blob/main/docs/05-repositories.md)。

## 2 已定与待定

已定（产品负责人，2026-11-17）：

- Python Agent 引擎改名 SanYuanAgent。
- 迁入本仓库 `CavaiLAB/sanyuan-agent`：先建仓库写文档，代码之后迁入。
- 它是工站、产线、工厂三级智能体的大脑，要能提供给这三级使用。
- 它是独立运行的 SDK：每个端都要用到它，包括机器人这类边缘设备，装上就能用。
- 模型服务由 Kun 提供；机器人这类设备本地可能还有小模型。

迁移的第一步（产品负责人，2026-11-17）：

- 先迁核心，服务层和媒体适配层以后再迁。
- 名字：发行名 `sanyuan-agent`，导入名 `sanyuan_agent`，命令行 `sanyuan-agent`，环境变量前缀 `NEUROAGENT_` 改成 `SANYUAN_AGENT_`。
- 带着历史导入：动过核心的提交都带过来，保留作者和时间，路径改写到新位置。
- 这一步不动原仓库：那里的一份照旧在用，不删、不改；让原仓库改为依赖新包是以后单独的一步。过渡期原仓库核心上的新改动要能同步过来。
- 核心保持 Apache-2.0，对所借鉴开源项目的声明保留。
- 本仓库公开，迁移结果直接推到这里。

待定：

| 事项 | 提议 |
|---|---|
| 服务层与媒体适配层的名字 | 跟着核心改。边界检查里先用了暂定名 `sanyuan_agent_app`、`sanyuan_agent_media` |
| 服务层与媒体适配层的许可 | 待定。平台的后端与前端已定全部用 MIT；服务层是否开放，还没有定 |
| 过渡期能不能先在本仓库对核心做行为上的改动 | 待定 |
| 本仓库的目录布局 | 见 [README](../README.md) 的「目录」一节 |
| 改名时没有改的各类标识、版权行里的旧项目名、`harness` 这个词 | 逐条列在 `tools/migration/rename/exceptions.tsv`，各自写了以后由谁定 |
| 发行物与安装形态 | 依赖分成最小安装与按需附加，面向哪些系统，要不要自包含的发行物，见[独立运行的 SDK](sdk.md)第 6、10 节。它不卡迁入 |
| 三级的部署形态 | 工站、产线、工厂三级各怎么部署、各依赖什么，待定，见[框架架构](architecture.md)第 13 节。它不卡迁入 |

## 3 改名涉及什么

- 包的发行名、导入名，以及全部源码里的导入语句与字符串形式的模块路径。
- 命令行入口的名字。
- 配置项与环境变量里带旧名字的前缀。
- 事件流、日志、追踪里出现的服务名。
- 文档与技能说明里的旧名字。

改名一次做完，不保留旧名字的别名包，也不保留旧环境变量前缀的兼容读取。原仓库那一份照旧用旧名字，等它改为依赖本仓库的包时再一起改（第 4 节第 4 步）。

不改的：别的进程、别的组件或别的仓库会按字面去认的名字，这一步不动，以后单独定。核心里实际碰到的是这几类：

- 宿主侧的包名：边界检查要靠它认出服务层、媒体适配层的包；改名后的对应名也一并加进了检查（暂定）。
- 遥测标识：指标名与 meter / tracer 的作用域名，已有的看板、告警按名字取数。
- 对外协议里报给对端的名字，外部服务上登记的资源名。
- 原产品桌面端的名字：安装包里的路径、打包产物的文件名。
- 版权人署名。

此外还有迁移工具本身、说明原名的文档、一份历史遗留的布局清单。逐条的清单（位置、写法、理由、以后由谁定）在 `tools/migration/rename/exceptions.tsv`，CI 的残留检查要求剩下的每一处旧名都登记在里面。

## 4 步骤

1. **导入（做完，2026-11-17）。** 带着历史把核心导入本仓库，做法见 [tools/migration/README.md](../tools/migration/README.md)。原仓库那一份照旧在用、不冻结。
2. **改名（做完）。** 按第 3 节一次改完：机械的部分由脚本做，可以重跑；要判断的几处单独提交、逐条说明。
3. **验证（做完，没有发包）。** 改名前后各跑一遍检查，用例的通过、失败、跳过与改名前完全一致；「核心不得引用服务层」的边界测试、「核心可以单独安装」的检查照旧生效，进了本仓库的 CI。发第一个包不在这一步。
4. **接回去（没做）。** 原仓库里用到引擎的地方，改为依赖本仓库发出来的包。
5. **收尾（没做）。** 原仓库的引擎目录删除，说明文档指向本仓库。

过渡期原仓库的核心上有新改动，要同步过来，做法（提议，已演练）见 [tools/migration/README.md](../tools/migration/README.md) 的「过渡期的同步」。

## 5 迁入之后要对齐的事

核心已经迁入，下面几项还没有做。

- **说明文档以代码为准重写。** 逐条对着代码核对，没有实现的写成规划。安全组件各自在哪些运行路径上启用，是要核对的第一项。
- **统一技能的 front matter。** 社区规范、平台的组件规格、引擎现有实现三处的字段有出入，对齐成一份；引擎对自定义技能的签名要求保留。
- **对接 Kun 的身份。** 迁入平台之后引擎改为以 `agent` 主体运行，这依赖 Kun 先启用 `agent` 主体与委托链。在那之前，引擎保持现有的身份形态。
- **统一事件流的契约。** 引擎输出的事件名与前端契约里的事件类型现在是两套，迁入时对齐成一份跨服务契约。
- **契约的出处。** 现在引擎引用的是原仓库里的契约目录。迁入之后改为引用平台级的契约，两套契约字段的差异在迁入前列清楚。
- **按 SDK 的形态发包。** 已定引擎是独立运行的 SDK。核心现在还没有作为包发布过。提议第一个对外版本就按这个形态发：依赖分成最小安装与按需附加，补齐运行的入口。离「装上就能用」还差什么，见[独立运行的 SDK](sdk.md)第 9 节。
- **与原仓库其他部分的接口。** 引擎的服务层和原仓库的 C# 服务之间有内部接口。迁入时把这些接口列成清单，逐个确定以后由 Kun 的哪项能力承接。
